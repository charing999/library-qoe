# Library QoE — 도서관 WiFi 체감 품질 예측

**KT 오픈데이터 챌린지 3위 수상작.** 도서관 WiFi 로그 9,193건(AP 4대, 2025-11-13 ~ 11-26)으로 체감 품질(QoE) 지표를 직접 설계하고, 5분 뒤 QoE를 예측해 좌석 선택에 쓰도록 만든 서비스입니다. GRU·CNN-LSTM·Transformer·LightGBM을 Persistence 기준선과 함께 비교했고, 그 결과 지표 설계가 예측 문제를 자명하게 만들었다는 점까지 아래에 정리했습니다.

## 왜 지표를 새로 만들었나

원본 로그에는 정답 레이블이 없습니다. 핑, 지터, 손실률, 속도, 신호 세기, 접속자 수만 있을 뿐이라 "이 자리가 쾌적한가"를 판단할 기준이 없어서 QoE 지표를 직접 정의했습니다.

- **로그 정규화.** 핑이 10ms에서 40ms로 오를 때의 체감 저하가 300ms에서 330ms로 오를 때보다 큽니다. 선형 정규화는 이 차이를 못 잡아서 `log1p` 스케일을 썼습니다.
- **가중치.** 수상 당시(v1)는 지연 0.25, 다운로드 0.25, 손실 0.20, 지터 0.15, RSSI 0.10, 접속자 수 0.05였습니다. 검증 결과 이 구성에 문제가 있어 v2로 다시 잡았습니다. 아래 결과 5 참고.
- **평활.** EWM(span=12)으로 순간 튐을 걸러냅니다. 좌석을 고르는 사람에게 필요한 건 1분짜리 스파이크가 아니라 앞으로 머물 구간의 추세입니다. 다만 이 평활이 예측 문제를 자명하게 만들었습니다. 아래 결과 참고.
- **3단계 변환.** 서비스가 보여주는 값은 연속값이 아니라 Good/Moderate/Bad입니다. 임계값은 학습 구간의 33/66 분위수로 잡았고 `backend/models/thresholds.txt`에 저장돼 있습니다.

정의는 `ml/qoe_features.py` 한 곳에 모아 학습과 서빙이 같은 산식을 쓰도록 했습니다.

## 데이터를 다시 보고 찾은 것

파일 한 개에 AP 4대가 시간순으로 섞여 있었습니다. 초기 코드는 이걸 한 줄기 계열로 보고 평활과 차분과 시프트를 전체에 걸었는데, 그러면 **연속한 두 행이 같은 AP일 확률이 30.6%**입니다. 나머지 69.4%는 지하 2층 값 다음에 1층 값을 놓고 "5분 뒤"라고 부르던 셈입니다.

수집 간격도 5분이 아니라 AP당 중앙값 1분이었습니다. "30분치로 5분 뒤를 예측한다"는 설명 자체가 사실과 달랐습니다.

지금은 평활·차분·타깃 시프트를 모두 AP별로 걸고, 시퀀스도 AP 경계를 넘지 않게 자르고, 학습·테스트 분할도 AP별로 뒤쪽 20%를 뗍니다.

| AP | 샘플 | 상태 전이 |
|---|---|---|
| 1F 104H | 2,418 | 232회 (9.6%) |
| 2F 207H | 930 | 72회 (7.8%) |
| B1F 0138 | 980 | 63회 (6.4%) |
| B2F 0155 | 4,741 | 363회 (7.7%) |

전이는 전체의 8.1%뿐입니다. 그래서 아무것도 안 하는 예측이 91.9%까지 맞습니다.

## 결과 2: 목적을 바꾸면 기준선은 0점입니다

서비스가 실제로 하려는 일은 QoE 값을 소수점까지 맞히는 게 아니라 **나빠지기 전에 알리는 것**입니다. 목적을 이렇게 두면 잴 것도 달라집니다. 상태가 바뀌는 순간만 떼어 재현율·정밀도·헛경보율을 봅니다.

| 모델 | 전이 재현율 | 전이 정밀도 | 악화 F1 | 헛경보율 | 방향 일치율 |
|---|---|---|---|---|---|
| GRU | 0.4519 | 0.1582 | 0.1446 | 0.1483 | 0.5285 |
| CNN-LSTM | 0.4327 | 0.1316 | 0.1795 | 0.1762 | 0.4860 |
| Transformer | 0.3942 | 0.1647 | 0.1957 | 0.1234 | 0.5106 |
| LightGBM | 0.3654 | 0.1949 | 0.2208 | 0.0931 | 0.4788 |
| **Persistence** | **0.0000** | **0.0000** | **0.0000** | **0.0000** | **0.0000** |

Persistence는 정의상 전이를 예측할 수 없어 구조적으로 0점입니다. 같은 데이터, 같은 예측인데 무엇을 재느냐에 따라 1등과 꼴찌가 뒤집힙니다.

다만 모델 쪽도 아직 쓸 만하지 않습니다. 전이를 40% 남짓 잡는 대신 정밀도가 0.13~0.19라 경고 다섯 번 중 넷이 헛것이고, 방향 일치율은 0.48~0.53으로 사실상 동전 던지기입니다. 지금 결론은 "모델이 낫다"가 아니라 **"비교가 성립하는 판을 만들었다"**까지입니다.

## 결과 3: 가중치 감도 분석

여섯 개 가중치는 도메인 직관으로 정한 값이라, 흔들었을 때 결과가 바뀌는지부터 확인했습니다.

```bash
python ml/weight_sensitivity.py
```

가중치에 곱셈 잡음을 준 200회 시행에서 3단계 라벨이 얼마나 유지되는지 봤습니다.

| 교란 강도 | 라벨 일치율 | 최저 | QoE 상관 |
|---|---|---|---|
| sigma=0.10 | 0.9711 | 0.9186 | 0.9994 |
| sigma=0.25 | 0.9302 | 0.7727 | 0.9964 |
| sigma=0.50 | 0.8695 | 0.5491 | 0.9839 |

웬만큼 흔들어도 라벨이 유지됩니다. 가중치를 소수점까지 방어할 필요는 없다는 뜻입니다.

그런데 항목을 하나씩 빼보니 **비중 0.20인 손실률을 통째로 제거해도 라벨이 98.8% 그대로**였습니다. 원인은 `packet_loss_rate`가 **97.3%의 행에서 0**이기 때문입니다. 변하지 않는 변수에는 가중치를 아무리 줘도 지표가 움직이지 않습니다.

| 항목 | 명목 가중치 | 실효 기여도 | 원본이 0인 비율 |
|---|---|---|---|
| norm_jitter | 0.15 | **0.317** | 0.0% |
| norm_ping | 0.25 | 0.272 | 0.0% |
| norm_speed | 0.25 | 0.190 | 0.0% |
| norm_rssi | 0.10 | 0.091 | 0.0% |
| norm_clients | 0.05 | 0.068 | 0.1% |
| norm_loss | 0.20 | **0.062** | **97.3%** |

실효 기여도는 가중치와 그 항목의 표준편차를 곱한 값입니다. 설계할 때 0.15로 가장 낮게 준 지터가 실제로는 가장 크게 기여하고, 0.20을 준 손실률은 거의 기여하지 않습니다. **명목 가중치와 실효 기여도는 다릅니다.** 가중치를 정할 때 각 지표가 이 환경에서 실제로 얼마나 변하는지를 안 봤던 것이 원인입니다.

## 결과 4: 타깃 정의를 바꾸면 모델이 기준선을 넘습니다

여기서부터는 검증 구간에서만 평가했습니다. 지금까지 테스트 구간을 여러 모델 비교에 반복해 썼는데, 시계열은 자기상관 때문에 한 줄기로 개선을 반복하면 과적합에 빠지기 쉽습니다. AP별로 앞 60%를 학습, 다음 20%를 검증으로 쓰고 마지막 20%는 건드리지 않았습니다.

```bash
python ml/experiment_target.py --horizon 1
```

| 타깃 | MAE | 기준선 MAE | 개선 | 전이 재현율 | 전이 정밀도 | 헛경보율 |
|---|---|---|---|---|---|---|
| smoothed (현재 방식) | 0.0154 | 0.0042 | -0.0112 | 0.5033 | 0.1723 | 0.2229 |
| **raw (평활 전 원계열)** | 0.0323 | 0.0329 | **+0.0006** | 0.5048 | **0.4973** | 0.3401 |
| delta (변화량) | 0.0045 | 0.0042 | -0.0002 | 0.1391 | 0.5000 | **0.0126** |

**표시용 평활과 예측용 계열을 분리하니 처음으로 모델이 기준선을 넘었습니다.** 전이 정밀도도 0.17에서 0.50으로 세 배가 됐습니다. 경고 다섯 번 중 넷이 헛것이던 것이 둘 중 하나로 바뀝니다.

변화량 타깃은 성격이 다릅니다. 재현율이 0.14로 낮은 대신 헛경보율이 0.0126으로 압도적으로 낮습니다. "놓쳐도 되지만 헛경보는 곤란하다"면 이쪽입니다. 두 방식은 우열이 아니라 운영 정책의 선택지입니다.

지평을 늘려도 순서는 유지됩니다. 15스텝에서도 raw만 기준선을 넘습니다(+0.0002).

## 결과 5: 지표에서 원인과 결과를 분리합니다 (QoE v2)

감도 분석에서 가중치가 아니라 **지표 구성 자체의 문제**가 드러났습니다. 원래 지표에는 RSSI와 AP 접속자 수가 들어가 있습니다. 그런데 이 둘은 품질을 만들어내는 **원인**이지, 이용자가 겪은 **체감**이 아닙니다. QoE는 "무엇을 겪었는가"를 재는 값이어야 하는데 "왜 그렇게 됐는가"를 15% 섞어 놓은 상태였습니다.

원인 변수가 체감을 얼마나 대변하는지 재봤습니다.

| 관계 | 상관 | R² |
|---|---|---|
| RSSI vs 체감 지수 | −0.113 | 0.013 |
| 접속자 수 vs 체감 지수 | +0.255 | 0.065 |
| 두 변수로 체감 지수 회귀 | | **0.065** |

두 변수를 합쳐도 체감의 6.5%밖에 설명하지 못합니다. RSSI는 부호마저 반대로, 신호가 나쁜 쪽이 체감은 오히려 조금 나은 것으로 나옵니다. 지수에 넣으면 체감과 거의 무관한 성분을 섞는 셈입니다.

### v2에서 바꾼 세 가지

**원인 변수를 지수에서 뺐습니다.** RSSI와 접속자 수는 예측 피처로만 남깁니다. 원인을 버리는 게 아니라 제자리로 옮기는 것입니다. 예측에는 여전히 유용하고, 나중에 "왜 나빠졌는가"를 설명할 때 쓸 수 있습니다.

**손실률도 뺐습니다.** 2.7%의 행에서만 0보다 크므로 연속 지수의 항목으로는 죽은 변수입니다. 대신 `loss_event` 플래그로 따로 다룹니다.

**가중치를 실효 기여도 기준으로 역보정했습니다.** 의도한 비중이 실제로 실현되도록 각 항목의 표준편차로 나눴습니다.

| 항목 | v1 가중치 | v2 가중치 | v2 실효 기여도 | 의도 |
|---|---|---|---|---|
| norm_ping | 0.25 | 0.365 | 0.385 | 0.385 |
| norm_jitter | 0.15 | 0.113 | 0.231 | 0.231 |
| norm_speed | 0.25 | 0.522 | 0.385 | 0.385 |
| norm_loss | 0.20 | 제외 → `loss_event` | | |
| norm_rssi | 0.10 | 제외 → 피처 | | |
| norm_clients | 0.05 | 제외 → 피처 | | |

v1과 v2의 3단계 라벨은 83.6% 일치합니다. 지표의 성격은 유지하면서 구성만 정리한 셈입니다.

### v2가 실제로 나은가

같은 검증 구간에서 v1과 v2를 나란히 돌렸습니다.

| 지표 버전 | 타깃 | 기준선 대비 | 전이 재현율 | 전이 정밀도 | 헛경보율 |
|---|---|---|---|---|---|
| v1 | raw | +0.0006 | 0.5048 | 0.4973 | 0.3401 |
| **v2** | **raw** | **+0.0008** | 0.4627 | **0.5162** | **0.2883** |
| v1 | delta | −0.0002 | 0.1391 | 0.5000 | 0.0126 |
| **v2** | **delta** | −0.0002 | **0.2174** | **0.5319** | 0.0130 |

raw 타깃에서는 헛경보율이 0.34에서 0.29로 떨어졌습니다. 변화량 타깃에서는 **헛경보율을 그대로 둔 채 전이 재현율이 0.139에서 0.217로 56% 올랐습니다.** 놓치던 전이를 더 잡으면서 헛경보는 안 늘었다는 뜻입니다.

원인 변수를 빼면 정보가 줄어 성능이 떨어질 것 같지만 반대였습니다. 지수에 섞여 있을 때는 체감과 무관한 변동으로 타깃을 흐리고 있었고, 피처로 옮기니 모델이 필요한 만큼만 쓰게 됐습니다. **원인은 지표가 아니라 설명 변수 자리에 있어야 합니다.**

```bash
python ml/experiment_target.py --horizon 1     # 기본값이 v2
```

서빙 중인 `backend/app.py`와 `gru_qoe.h5`는 아직 v1 기준입니다. v2로 옮기려면 재학습이 필요해 그대로 뒀습니다.

## 정리

평가 지표를 정하지 않은 채 MSE만 보고 있었다면 이 프로젝트는 잘 맞는 모델처럼 보였을 것입니다. 기준선을 계산해서 문제 설정이 잘못됐다는 걸 알았고, 데이터를 다시 봐서 AP가 섞여 있다는 걸 찾았고, 목적을 다시 정의해서 비교가 성립하는 지표를 만들었습니다. 남은 일은 그다음입니다.

다섯 단계를 거쳤습니다. 기준선을 계산해 문제 설정이 잘못됐다는 걸 알았고, 데이터를 다시 봐서 AP가 섞여 있다는 걸 찾았고, 목적을 다시 정의해 비교가 성립하는 지표를 만들었고, 그 지표 위에서 타깃 정의를 바꿔 처음으로 기준선을 넘었고, 지표에서 원인과 결과를 분리해 전이 재현율을 56% 올렸습니다.

남은 일입니다.

- raw 타깃과 delta 타깃 중 무엇을 쓸지는 헛경보를 얼마나 감수할지에 달렸습니다. 이용자에게 물어볼 문제입니다
- 검증 구간에서 정한 설정으로 테스트 구간을 마지막에 한 번만 봅니다
